## 📋 User Management

### Development: `users.local.json`

**Location**: `./users.local.json` (never committed to git)

**Never run in production!** This file is for local development only.

**Usage**:
```bash
# Development - credentials loaded from users.local.json
# Backend reads from environment or file during dev
```

**Security Note**:
- The `users.local.json` file includes both hashed and plain-text dev passwords
- Plain-text passwords (`_dev_password` field) are for reference only
- **NEVER** expose these in frontend code
- Always use hashed passwords in authentication

## 🔑 Credential Format

### Bcrypt Hashed Passwords

All passwords in `users.local.json` are hashed with:
- **Algorithm**: bcrypt
- **Cost**: 12
- **Salt**: Automatically generated by bcrypt

**Example**:
```php
// To hash a password
$hashed = password_hash('mypassword', PASSWORD_BCRYPT, ['cost' => 12]);

// To verify
if (password_verify('mypassword', $hashed_from_db)) {
    // Password matches
}
```

## 🔐 Production Guidelines

### DO NOT
- ❌ Commit `users.local.json` to git
- ❌ Store passwords in frontend code
- ❌ Display credentials in UI
- ❌ Use hardcoded passwords
- ❌ Send passwords in URLs or query strings
- ❌ Store plain-text passwords in database
- ❌ Use weak password hashing (use bcrypt, scrypt, or Argon2)

### DO
- ✅ Use environment variables for secrets
- ✅ Hash all passwords with strong algorithm (bcrypt cost 12+)
- ✅ Use HTTPS/TLS in production
- ✅ Implement rate limiting on login endpoint
- ✅ Log all authentication attempts
- ✅ Use JWT with appropriate expiration times
- ✅ Implement account lockout after failed attempts
- ✅ Use strong, unique tokens
- ✅ Validate all inputs server-side
- ✅ Use prepared statements (parameterized queries)

## 🛡️ Production Deployment

### Step 1: Create Production User Store

**Option A: Environment Variables**
```bash
export DB_ADMIN_EMAIL="admin@production.com"
export DB_ADMIN_HASH="$2y$12$hashed_password_here"
```

**Option B: Secure Secret Manager**
- AWS Secrets Manager
- Azure Key Vault
- HashiCorp Vault
- Kubernetes Secrets

**Option C: Database (Recommended)**
```sql
-- Create users table
CREATE TABLE users (
    user_id INT PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    nome VARCHAR(100),
    cognome VARCHAR(100),
    ruolo VARCHAR(50),
    stato VARCHAR(50),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
);
```

### Step 2: Backend Configuration

**File**: `backend/config/auth.php`
```php
<?php
// Load users from environment or database
$users = [
    'admin' => [
        'email' => getenv('ADMIN_EMAIL'),
        'hash' => getenv('ADMIN_PASSWORD_HASH'),
        'role' => 'admin'
    ]
];
?>
```

### Step 3: Update AuthController

Modify `backend/api/controllers/AuthController.php`:
```php
public function login($data) {
    // Never hardcode credentials
    // Load from environment, database, or secret manager
    
    $user = $this->loadUserFromSecureSource($data['email']);
    
    if ($user && password_verify($data['password'], $user['password_hash'])) {
        return $this->generateJWT($user);
    }
    
    return false;
}
```

## 🔑 JWT Token Security

### Token Structure
```
Header: { "alg": "HS256", "typ": "JWT" }
Payload: { "user_id": 1, "email": "admin@armory.local", "role": "admin", "exp": 1234567890 }
Signature: HMACSHA256(header.payload, secret_key)
```

### Security Best Practices
- **Expiration**: 1 hour (3600 seconds)
- **Refresh Token**: 7 days for refresh (implement if needed)
- **Storage**: localStorage (acceptable for this project)
- **Secret Key**: Use strong, random key (min 32 bytes)
- **HTTPS Only**: Always use HTTPS in production
- **HttpOnly Cookies**: Use for enhanced security (if possible)

## 🔍 Audit & Logging

### Authentication Events to Log
```php
// Log successful login
error_log("[AUTH] User {$email} logged in successfully");

// Log failed login attempts
error_log("[AUTH] Failed login attempt for {$email}");

// Log token validation failures
error_log("[AUTH] Invalid token from {$ip}");

// Log unauthorized access attempts
error_log("[AUTH] Unauthorized access attempt to {$resource} by {$email}");
```

### Logging Best Practices
- Never log passwords or tokens
- Include timestamp, user email, action, and IP address
- Store logs securely (separate from application)
- Rotate logs regularly
- Monitor for suspicious patterns

## 📊 Role-Based Access Control (RBAC)

### Defined Roles
1. **admin**: Full system access
2. **capo_sm**: Chief of Staff - view statistics
3. **armaiolo**: Armourer - manage equipment
4. **ufficiale**: Officer - manage personnel
5. **operatore**: Operator - view assignments

## 🔄 Incident Response

### If Credentials are Exposed

1. **Immediate**:
   - Revoke all active tokens
   - Change all exposed credentials immediately
   - Update all environments

2. **Investigation**:
   - Review access logs for unauthorized access
   - Check for data breaches
   - Audit all recent changes

3. **Communication**:
   - Notify affected users
   - Document the incident
   - Update security procedures

4. **Prevention**:
   - Implement automated secrets scanning
   - Enforce code review process
   - Add pre-commit hooks to detect secrets
